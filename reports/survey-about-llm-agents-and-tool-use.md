# LLM Agents and Tool Use: A Survey of Architectures, Training, Evaluation, and Safety

## TL;DR

- **The core architecture has barely changed since 2022.** Nearly every tool-using agent today is a descendant of the ReAct loop — interleaving a natural-language reasoning trace with an action (tool/API call) whose observation is fed back into the next reasoning step; ReAct beat imitation- and RL-trained baselines by +34% absolute success on ALFWorld and +10% on WebShop with only one or two in-context examples [1][2].
- **Tool use moved from prompting to interfaces and training.** What began as prompt engineering (Toolformer's self-supervised API learning [3]) and dataset construction at scale (ToolLLM's 16,464 RapidAPI endpoints [4][5]) has consolidated into native function-calling schemas, strict-mode JSON conformance, and on-demand tool search [6], with tool-call formats baked into model chat templates [7].
- **Capability is real but reliability is not.** Single-turn function-call accuracy is close to saturated (gpt-4o at ~94–95.5% on simple/parallel AST matching), yet the same models collapse on multi-turn agentic categories (BFCL "Memory" = 6.0) [8], and pass^k on τ-bench falls from ~61% at k=1 to under 25% at k=8 in retail despite <50% mean task success [9].
- **Long-horizon execution is where agents actually fail.** Reported pass@1 declines from 76.3% on short tasks to 52.0% on very long ones, with software-engineering Graceful Degradation Scores collapsing from 0.90 to 0.44, and naive memory scaffolds hurting every model tested [10][11].
- **Security and interoperability are the new frontier.** Indirect prompt injection through tool outputs is measurable and severe (57.7% targeted attack success against GPT-4o on AgentDojo, up to 70% when injected at the end of a tool response) [12], while MCP and A2A are standardizing the tool and agent-to-agent boundaries respectively [13][14].

## Background

An **LLM agent** is a system in which a language model is placed in a loop that lets it perceive an environment, decide on an action (usually an external call to a tool, API, function, or environment primitive), observe the result, and continue until a goal is met. **Tool use** is the mechanism by which a text-only model escapes its training distribution — fetching live facts, performing exact arithmetic, executing code, or mutating state in an external database [1][3].

The reason this matters *now* is that tool use has shifted from a research curiosity to the primary product surface for frontier models: the same models are evaluated on function-calling leaderboards, deployed behind protocol servers, and graded on end-state task success rather than text quality [8][13]. It also matters because the failure modes are qualitatively different from ordinary hallucination. A model that invents a fact hallucinates text; a model that invents a *tool argument* takes an irreversible action — τ-bench measured 6.34 non-existent-ID tool calls per retail task for a weaker agent versus 0.46 for a stronger one [9].

The intellectual lineage is short and traceable. **Chain-of-Thought** prompting established that intermediate reasoning steps materially improve complex reasoning, with 8 exemplars on a 540B model reaching state-of-the-art GSM8K accuracy [15]. **ReAct** then married that reasoning substrate to acting, using reason→act→observe steps so that the reasoning trace plans and updates action selection while observations ground reasoning [1][2]. **Toolformer** demonstrated the complementary result that tool invocation itself can be learned self-supervised from a handful of demonstrations per API, deciding which API to call, when, with what arguments, and how to fold the result back in [3]. Those three papers define the field's default scaffold.

## Foundations: from prompting tool use to native function calling

**Interleaved reasoning and acting.** ReAct's contribution is architectural rather than algorithmic: by emitting thoughts and actions in one autoregressive stream, the model uses its reasoning to induce, track, and correct action plans, and uses action observations to reduce hallucination and error propagation relative to CoT alone on HotpotQA and Fever [1]. On ALFWorld the best ReAct trial reached 71% success versus 45% for act-only prompting and 37% for the imitation-learning agent BUTLER; on WebShop it added roughly 10 points absolute, all with one or two examples [2]. Plan-and-Solve later generalized the "decompose before you execute" idea for zero-shot settings, motivated by an error analysis of Zero-shot-CoT showing 7% calculation, 12% missing-step, and 27% semantic-misunderstanding failures on GSM8K [16].

**Self-supervised and dataset-driven tool learning.** Toolformer is the canonical demonstration that tool use is learnable rather than merely promptable: a model trained to insert API calls in text learned to use a calculator, a Q&A system, two search engines, a translator, and a calendar, improving zero-shot performance without degrading core language ability [3]. ToolLLM scaled this to the messy real world, harvesting **16,464 RESTful APIs across 49 categories** from RapidAPI Hub, auto-generating single- and multi-tool instructions with solution paths, and introducing the DFSDT depth-first decision-tree search over reasoning traces [4][5]. The quantitative payoff was large: on ToolEval (which agrees with human annotators 87.1% on pass rate and 80.3% on win rate), ChatGPT with ReAct averaged 40.2% pass rate versus 64.8% with DFSDT, GPT-4 went from 57.2% to 71.1%, and the fine-tuned ToolLLaMA reached a 66.7% average pass rate — competitive with its ChatGPT teacher and second only to GPT-4 [5]. This is an early and important signal that **structured search over action sequences beats a single greedy trajectory**.

**Retrieval-aware API calling.** Gorilla framed API calling as retrieval plus fine-tuning rather than pure generation. Using APIBench (~1,600 ML APIs across TorchHub, TensorHub, and HuggingFace) and AST sub-tree matching that separates functional errors (wrong API) from hallucinations (invented API), a fine-tuned LLaMA-7B surpassed GPT-4 by **20.43 percentage points** in zero-shot AST accuracy, and oracle retrieval during training added +12.37% (TorchHub) and +23.46% (HuggingFace) [17]. The flip side is equally instructive: a weak retriever (BM25) can degrade accuracy substantially, meaning retrieval quality — not model quality — is often the bottleneck. That concern has aged well: a dedicated tool-retrieval benchmark found off-the-shelf retrievers are "not tool-savvy" [18], motivating reasoning-distilled retrievers that align queries with synthetic tool descriptions [19].

**The interface transition.** The most consequential practical change is that tool use stopped being something you prompt and became something the API models natively. In the OpenAI-style interface, tools are declared as JSON schemas in a `tools` parameter, the model returns a structured call with a `call_id`, `name`, and JSON `arguments`, the application executes it and returns the output, and `strict` mode enforces exact schema conformance; `tool_choice` controls whether invocation is automatic, required, or forced [6]. For large tool ecosystems, on-demand **tool search** lets the model defer loading tool definitions and fetch only what it needs, which is the interface-level analogue of the retrieval problem Gorilla and ToolLLM attacked [6][18]. On the open-model side, tool calling is encoded directly into chat templates — llama.cpp ships native format handlers for Llama 3.x, Functionary, Hermes, Qwen 2.5, Mistral Nemo, and Command R, with a generic fallback and optional parallel calls [7]. Enterprises have followed suit: Granite-20B-FunctionCoding added function calling through multi-task learning over granular subtasks rather than treating it as an emergent property [20]. A third scaling strategy sidesteps context entirely — ToolkenGPT represents each tool as a learned "toolken" embedding inserted into the vocabulary, letting a *frozen* model address an arbitrary, growing tool set [21]. Finally, the pipeline itself can be made trainable: symbolic learning reframes prompts, tools, and their composition as learnable weights optimized by language-based backpropagation, enabling agents that update their own tooling after deployment [22].

## Planning, reflection, and search over reasoning paths

**The reasoning substrate.** CoT [15] and its tool-aware variants set the ceiling for everything downstream. Chain-of-Abstraction is the clearest tool-specific adaptation: it decodes abstract reasoning chains containing placeholders and then parallelizes the tool calls that "reify" them, reporting roughly 6% absolute QA accuracy improvement and ~1.4× faster inference versus baseline tool-augmented LLMs [23].

**Iterative self-correction.** Self-Refine uses a single frozen model as generator, critic, and refiner, improving performance by about 20% absolute on average across seven tasks (e.g., GPT-4 code optimization 27.3% → 36.0%), with clearly diminishing returns across up to four iterations [24]. Reflexion converts environment feedback into verbal self-reflections stored in episodic memory and reached 91% pass@1 on HumanEval, above the 80% prior GPT-4 result — notably without any weight updates [25]. Agent-R pushes the same idea into training, teaching agents to reflect and recover from errors in real time via iterative self-training with MCTS [26].

**Search over trajectories.** Tree-of-Thoughts generalizes CoT into search with self-evaluation and backtracking, lifting Game-of-24 success from 4% (CoT) to 74% [27]. Language Agent Tree Search (LATS) is the tool-use analogue, replacing ReAct's single trajectory with MCTS over reasoning-acting steps plus a learned value function; it reached 92.7% pass@1 on HumanEval with GPT-4 versus 80.1% for base GPT-4, and 75.9 on WebShop versus 53.8 for ReAct [28]. The natural reading is that **breadth plus backtracking substitutes for model strength** on multi-step tasks where a single greedy path is likely to enter a bad state — consistent with the ToolLLM DFSDT result [5].

**Does the scaffolding actually help?** This is more contested than the headline numbers suggest. A sensitivity analysis of ReAct-style prompting found that gains were driven mostly by similarity between prompt exemplars and queries (i.e., approximate retrieval) rather than by the interleaved reasoning structure itself, directly challenging the original interpretation [29]. Long-horizon studies compound the skepticism: a documented "self-conditioning" effect shows per-step accuracy *degrades* as a task progresses because the model's own past errors sit in context, and this is not fixed by scaling model size [10]; a 396-task, 23,392-episode reliability study found pass@1 falling from 76.3% (short tasks) to 52.0% (very long tasks), Graceful Degradation Scores dropping from 0.90 to 0.44 in software engineering, and naive episodic-memory scaffolds *hurting* long-horizon scores for all ten models tested [11]. Iterative reflection and search are thus best understood as variance-reduction techniques with real token costs — not as free capability gains.

## Evaluation: benchmarks, metrics, and skepticism

**A two-family taxonomy.** Tool-use evaluation splits into (a) *static* benchmarks that score the correctness of a generated call against a fixed schema, and (b) *interactive* benchmarks that place the agent in a stateful environment and score final task success. This distinction is not academic: a model can score highly on call validity while failing the underlying task, which is precisely the gap the field's most pointed critiques target [30][8].

**Static call-correctness benchmarks.** The Berkeley Function Calling Leaderboard (BFCL) is the de facto standard, scoring serial and parallel calls in multiple languages with AST evaluation, plus executable REST-API evaluation and a dedicated *relevance detection* category in which the correct behavior is to call *no* function — an explicit hallucination test [8]. The pattern that emerges is saturation at single turn and collapse at multi-turn: gpt-4o-2024-11-20 reaches 94.0–95.5% AST accuracy on multiple/parallel simple functions but drops to 35.5 on agentic web search and 6.0 on agentic memory [8][31]. BFCL's own LLM-judge error analysis identifies "Failed to Understand Environment State" — hallucinating or assuming the wrong environment state — as the most prevalent multi-turn failure [31]. ToolSandbox (Apple) adds stateful tool execution with implicit cross-tool state dependencies, an LLM user simulator, and a milestones/minefields dynamic evaluation over 1,032 cases; it is notable for finding that the same outcome is often reachable by many different trajectories, undermining exact action matching as a metric [30]. API-Bank is the earlier training-and-evaluation benchmark in this family [32], and ToolBench's dataset of 16,464 APIs and 126,486 instances remains the largest raw tool-use corpus [4][5].

**Interactive agent benchmarks and the human gap.** WebArena's 812 long-horizon tasks on self-hosted websites are graded by end-state functional correctness; the best GPT-4 agent succeeded on 14.41% versus 78.24% for humans, and GPT-4 wrongly declared 54.9% of feasible tasks impossible [33]. OSWorld's 369 real desktop tasks show agents at 0.99–12.24% versus 72.36% for humans [34]. GAIA's 466 real-world questions show humans at ~92% versus ~15% for GPT-4 with plugins [35]. SWE-bench's 2,294 real GitHub issues started at 1.96% resolve rate for Claude 2, with SWE-agent later reaching 12.47% [36]. BrowserGym provides the shared harness that makes such web-agent comparisons possible [37].

**Measuring reliability, not just success.** τ-bench's most durable contribution is the **pass^k** metric — all k i.i.d. trials must succeed — as distinct from pass@k, which only needs one. It exists because real deployments need consistency, and the numbers justify the pessimism: gpt-4o reaches roughly 61% pass^1 in retail and ~35% in airline, but pass^8 falls below 25% in retail, with overall task success under 50% [9]. Benchmarks in the same family now report min–max accuracy across runs rather than a single number, and best-practice work for agentic benchmarks codifies such rigor requirements [11][37]. Reproducibility caveats are structural: ToolBench's dependence on live RapidAPI endpoints introduces high variance, and LLM-simulated users can hallucinate or drift, confounding evaluation itself [8][30].

**Skeptical results.** The strongest corrective in the literature is "An Illusion of Progress?", which evaluated 300 tasks across 136 live websites and found most frontier web agents succeed on only about 30%, far below earlier WebVoyager-reported numbers, with OpenAI Operator at 61% as the best performer [38]. The authors attribute earlier optimism to benchmark shortcomings — leakage, unrealistic tasks, weak judges — and propose an LLM judge (WebJudge) reaching ~85% human agreement with only a ~3.8% success-rate gap [38]. This echoes the broader point that **static tool-call correctness is not task success** [30][8].

## Training and protocols: agentic RL and standardized interfaces

**Agentic RL as a distinct paradigm.** A major survey synthesizes 500+ works to argue that agentic RL is not simply LLM-RL applied to agents: conventional LLM-RL is a degenerate single-step MDP, whereas agentic RL is a temporally extended POMDP in which the model acts on partial observations, and it is organized around capabilities — planning, tool use, memory, reasoning, self-improvement, perception [10]. VerlTool operationalizes this as "Agentic RL with Tool use," standardizing tool APIs across code execution, search, SQL, and vision, and reporting near-2× speedup from asynchronous rollout execution across six domains [39].

**Where agentic RL breaks.** RL-only tool-use training is unstable in specific, documented ways. One study reports *catastrophic collapse* in multi-step tool-use RL driven by probability spikes in control tokens — the underlying capability survives but is obscured by broken invocation formatting — with interleaved SFT+RL substantially stabilizing training at some cost to out-of-distribution generalization; a related line quantifies interference between reasoning and tool-use behaviors [40]. Related work targets the opposite failure, tool *over-use*, by learning difficulty-aware rewards for "when not to act" [10], and environments that internalize dynamics to improve long-horizon tool use are treated as a first-class training problem in the same survey [10]. The practical reading: tool-use behavior is fragile enough that training curricula and reward shaping matter as much as scale.

**Protocol standardization.** Two complementary layers have emerged. **MCP (Model Context Protocol)** standardizes the host↔tool/context boundary as an open, stateless JSON-RPC 2.0 protocol with per-request capability negotiation, resources/prompts/tools on the server side and elicitation/sampling on the client side, plus opt-in extensions [13]. **A2A (Agent2Agent)** standardizes agent↔agent interoperability using Agent Cards for discovery, asynchronous long-running tasks, and "opaque execution" that deliberately avoids exposing internal state, memory, or tools — layered over HTTP, JSON-RPC 2.0, SSE, or gRPC [14]. Between them sits the OpenAI-style function-calling schema as the model→application contract [6]. The design philosophy is telling: MCP is stateless and capability-negotiated, and A2A makes opacity a feature, both indicating that the community considers loose coupling a security and interoperability requirement rather than an implementation detail [13][14].

**Safety: indirect prompt injection is the defining threat.** Because agents must consume untrusted data returned by tools, the tool result is a first-class attack surface. AgentDojo measured this systematically across 97 tasks and 629 security test cases and found **inverse scaling** — more capable models were *easier* to attack — with an "Important message" attack reaching 57.7% targeted attack success against GPT-4o (dropping to ~7.5–8% with a tool-filter defense), and injections placed at the end of a tool response reaching up to 70% success [12]. MCP-specific research maps the attack surface across the server lifecycle [41], enumerates 31 distinct attack methods [42], and covers tool squatting and rug-pull attacks mitigated by signed tool definitions and policy-based access control [43]. A further caution concerns measurement itself: an audit found harness defects — undelivered payloads and scoring by tool identity rather than argument content — that inflated reported attack success rates dramatically, with a tool-identity scorer reporting 21.7% attack success where true argument-level success was 1.2%, and a model previously reported at 62.8% scoring 0% under a corrected harness [12][41]. On the defense side, training-time approaches include self-reflection fine-tuning on the agent's own compromised trajectories [12], alongside pre-execution action auditing and the tool-filtering guards AgentDojo evaluated [12].

## Multi-agent systems and memory

**The multi-agent debate has numbers on both sides.** Anthropic's orchestrator–worker research system (a lead model delegating to parallel subagents) outperformed a single-agent baseline by 90.2% on an internal research evaluation and cut research time substantially, but consumed roughly **15× the tokens** of a chat interaction (agents generally ~4×) — an explicit cost-benefit trade rather than a free win [44]. Cognition's "Don't Build Multi-Agents" argued the opposite, that parallel writers produce fragile and inconsistent systems, and their follow-up narrowed the claim: multi-agent architectures work only when writes stay single-threaded and extra agents contribute *intelligence* rather than *actions* [45]. Independent evidence supports caution — self-organizing LLM teams failed to match their best individual expert by up to 37.6% through "integrative compromise" that averages expert and non-expert views [46] — and a failure taxonomy identifies 14 distinct failure modes spanning specification, inter-agent misalignment, and task verification [47].

**Coordination signals are themselves unreliable.** Self-reported model confidence turns out to be a poor basis for combining agent answers: across an 18-model pool, higher mean confidence correlated with *lower* accuracy, and when one of two answers was correct the more confident responder was right only 42% of the time — worse than chance [48]. Runtime, model-specific confidence calibration raised correct-answer selection to 81% on HumanEval/MBPP from roughly 50%, indicating that much of the multi-agent gap is a calibration problem rather than a reasoning problem [48].

**Memory and context are the central engineering constraint.** Long-horizon agents fail largely because context accumulates unboundedly and degrades. Approaches treat context maintenance as a callable tool rather than an append-only log to avoid semantic drift [49], and dedicated benchmarks now measure memory as a competency in its own right, including incremental multi-turn memory evaluation [50]. The empirical finding that naive memory scaffolds *hurt* long-horizon performance [11] suggests the field has not yet found the right abstraction, and the documented "context rot" effect on decision quality supports treating context curation as the primary reliability lever for tool-heavy agents [45][49].

## Trends and open problems

**Trend 1: from prompt engineering to interface and protocol engineering.** The most durable two-year change is that tool use is now specified rather than coaxed. Native function calling with strict schema conformance [6], tool-call formats in chat templates [7], stateless capability-negotiated MCP servers [13], and opaque agent-to-agent A2A communication [14] together mean interoperability is becoming a standards problem rather than a modeling problem. This shifts research attention toward retrieval over large tool libraries [18][19] and on-demand tool loading [6].

**Trend 2: evaluation is moving from accuracy to reliability.** pass^k [9], min–max reporting across runs [37], rigorous agentic benchmark best practices [11], and Graceful Degradation Scores [11] all express the same insight: a system that succeeds 60% of the time independently is not a 60%-reliable system, and averaging hides the cliff. This is arguably the field's healthiest development, because it makes the gap between leaderboards and deployments legible.

**Trend 3: the reasoning/acting boundary is being renegotiated.** Chain-of-Abstraction's placeholder-then-reify pattern [23], agentic RL's treatment of planning and tool use as jointly learned POMDP behaviors [10], and the discovery that reasoning and tool-use objectives *interfere* during RL [40] all suggest that the clean separation implied by "think then act" is a simplification the field is outgrowing.

**Open problem 1: long-horizon error compounding.** Self-conditioning degrades per-step accuracy and is not fixed by scale [10]; pass@1 falls ~24 points from short to very-long tasks and naive memory scaffolds hurt every model tested [11]. No architecture in this survey solves it; search and reflection mitigate variance on specific benchmarks [27][28] but are not known to flatten the compounding curve.

**Open problem 2: security under untrusted tool output.** Inverse scaling on prompt injection [12], an MCP attack surface spanning the full server lifecycle [41][42], and tool squatting/rug-pull vectors [43] point to a structural problem rather than a patchable bug: the agent's design requirement (consume untrusted data) is in direct tension with its autonomy. The measurement audit showing harness defects inflated attack-success rates by an order of magnitude [12] means even the defense literature is not yet on stable footing.

**Disputed results.** Three specific claims remain contested. (i) *Do ReAct-style loops help because of reasoning, or because of exemplar–query retrieval?* The sensitivity analysis argues the latter [29], directly contradicting the original framing [1][2]. (ii) *Do multi-agent systems add value?* Industry sources disagree in print — a 90.2% improvement on an internal eval at ~15× token cost [44] versus an argument that multi-agent fragility makes single agents preferable [45] — and independent studies find team losses up to 37.6% against best experts [46]. (iii) *Do benchmark scores reflect capability?* Reported web-agent success rates diverge by roughly a factor of two depending on benchmark and judge [38], and best-practice work documents the methodological reasons why [11].

**What to watch.** Tool retrieval quality as the practical bottleneck for large tool libraries [18][19]; training curricula that keep tool-use behavior stable under RL [40][39]; calibration rather than ensemble size as the lever for multi-agent gains [48]; and context curation as a first-class, learned capability rather than a prompt trick [49][50].
